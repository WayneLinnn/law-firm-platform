## 1. 定位与核心主张

> **以案件为中心的律所操作系统**：检索不是一个功能页，而是嵌在每个办案节点里自动发生的事。

### 一条主线

```
 ①接案        ②立案         ③办案（循环）      ④交付        ⑤收钱
────────    ─────────    ──────────────    ────────    ────────
 客户来了  →  能不能接  →   查 → 写 → 审   →  文书交付  →  出账收款
              (利冲)        ↑________↓
```

**检索和生成 = 第③步里的两个动作，不是并列的独立功能。**

### ③办案循环内部

```
        案件上下文（案由·事实·争议焦点·对方主张）
                      ↓
   ① 查   检索法条+类案，产出结构化引用
                      ↓
   ② 写   基于引用生成文书，每句话挂着出处
                      ↓
   ③ 审   机器校验（条号/案号真伪·时效） + 律师确认签字
                      ↓
          不过 → 回 ①或②     通过 → 定稿归档
```

三个不可动摇的设计：

1. **查必须带案件上下文** —— 这是平台相对于"一个搜索框"的全部价值
2. **写的产出必须带引用锚点** —— 律师能点开任一句看出处，这是他敢签字的唯一前提
3. **审是双层：机器 + 人** —— 机器管真伪，人管判断

| iCourt Alpha | 项目模板把方法论产品化；律所管理闭环；Word 插件 | 模板写死；封闭无 API；重实施 |

| 序 | 需求 | 后果 | 对应 |
|---|---|---|---|
| 1 | 别漏时限 | 漏一次赔执业险 | 时限引擎（Step 15） |

## 3. 架构与铁律

```
接入层    Next.js Web  │  Word 插件  │  小程序
业务层    modules/*                        可独立装卸
流程层    WorkflowPort   实现 = LangGraph（Step 9）
契约层    kernel/ports   业务代码只认这里
实现层    adapters/*     DeepSeek、MinIO、法律检索服务
数据层    Postgres（每模块独立 schema）/ Redis / MinIO
```

依赖只能向内：`modules ──▶ kernel.ports ◀── adapters`

**流程层和能力层必须分开**：流程是你画死的（可审计），能力是模型干的（会犯错）。模型只在节点内部自由发挥，**永远不决定下一步走哪**。这是律所平台和通用 AI 助手的根本区别。

### 什么是"极小内核"

判断标准一句话：**把所有业务模块删光，剩下还跑得起来的那部分，就是内核。**

| 文件 | 干什么 |
|---|---|
| `kernel/registry.py` | 模块注册表：发现 / 依赖校验 / 拓扑排序 / 装卸 / 降级 / 能力汇总 |
| `kernel/ports/` | 契约：定义"模型/检索/编排/存储该长什么样"，不写实现 |
| `kernel/container.py` | 接线板：启动时把契约接到具体实现上 |
| `kernel/db/` | 数据库底座：连接、每模块独立 schema、多分支迁移 |
| `kernel/web/` | HTTP 装配：建 app、统一错误映射、挂各模块路由 |

**"极小"= 只放"换掉任何一个业务模块都不需要改"的东西。**
内核不知道什么是"案件""利冲""计时"。它现在不到 1000 行，以后基本不会再长。

### 三条铁律（`scripts/check_boundaries.py` 强制，CI 必跑）

1. 业务模块只能 import `kernel.*`，**不得 import 任何 `adapters.*`** —— 要外部能力用 `container.get("model")`
2. 模块之间只能 import 对方的 `api.py`，**禁止跨 schema 查表** —— 用 `registry.api()` / `registry.optional_api()`
3. 每个模块自带 `migrations/`，是一条独立 Alembic 分支，**删模块 = 代码与建表脚本一起消失**

### 模块目录（无一例外）

```
backend/modules/<name>/
  manifest.py    声明依赖、权限点、capabilities        【必须】
  api.py         对外唯一出口，只 re-export            【必须】
  service.py     业务逻辑
  models.py      ORM，__table_args__ = schema_of("<name>")
  router.py      定义 router = APIRouter()，内核自动挂 /api/<name>
  migrations/versions/   本模块自带的迁移
```

### 每个模块的固定五步

```
1. 定契约   写 api.py 签名 + Pydantic 数据类，不写实现
2. 写测试   针对接口写用例，此时全红
3. 建模型   models.py + 迁移
4. 填实现   service.py，直到测试全绿
5. 接路由   router.py
```

### 每步统一的完成标准

- [ ] 接口先写、测试先红、实现后绿
- [ ] 独立 schema，无跨模块查表
- [ ] 界面上能走通一次真实场景
- [ ] `python -m kernel.cli check` 通过
- [ ] 拆卸测试：停用本模块，系统仍能启动

### 4.1 它是什么

| 维度 | 现状 |
|---|---|
| 数据 | SQLite `data/lawlib.db` 29MB：**919 文档 / 5194 切片**（判例 911，法条 8） |
| 向量 | `data/vectors.npy` 15MB，**bge-base-zh-v1.5 本地模型**，768 维，不花 API 钱、**数据不出境** |
| 检索 | BM25(FTS5 trigram) + 向量 + **RRF 融合** + **精确条号置顶** |
| 编排 | LangGraph 13 节点，3 处循环 + 快路径 + HITL 中断 |
| 防幻觉 | 只用参考资料+带【S编号】/ 引用校验(条号案号真伪) / 时效标记 |
| 工具 | 诉讼时效、逾期利息(LPR分段)、诉讼费 —— Python 算，不让模型心算 |
| 评测 | 30 题金标：混合+重排 R@10=1.00，MRR 0.527（纯 BM25 仅 0.304） |
| 模型 | OpenAI `gpt-5.6-luna` —— 要换 DeepSeek |
| Python | 3.9.20 —— 要升 3.12 |

**它填的是能力层，不是流程层。** 你要新建的是上面三层（流程、业务、界面）。

### 4.2 关键接口

```python
search.hybrid(q, n=8, doc_type=None) -> List[dict]          # 纯检索，0 成本
lc.retriever.LawRetriever(n=8, rerank=True).invoke(q)       # -> List[Document]

```

`Document.metadata` 已含：案号 / 法院 / 法院层级 / 地域 / 案由 / 效力层级 / 指导案例号 / 入库编号 / 失效依据 / 文号 / 施行日期 / source / exact

SQLite schema：

```
documents(id, sha1, doc_type[statute|case], title, file_path, n_chars, meta:JSON, added_at)
chunks(id, doc_id, ordinal, label, title, locator, text, n_chars)
chunks_fts  -- FTS5 trigram，外部内容表指向 chunks
```

### 4.3 接入方式：独立进程 + HTTP

```
backend (FastAPI)
   modules/retrieval ──▶ kernel.ports.RetrievalPort / LegalQAPort
                              ▲
                              │ HTTP
                  adapters/retrieval/legal_rag_http.py
                              │
                              ▼
   法律检索服务 (独立进程 + 独立 venv, FastAPI 薄壳)
     lc.graph / lc.retriever → SQLite + vectors.npy
```

理由：bge 模型加载慢不能拖累主应用重启；langchain / torch 依赖不污染主应用；RAG 有爬虫、建库、向量化等长任务，生命周期与业务应用无关。

**注意**：虽然两边同为 Python，也**不要 in-process import**。边界是刻意的。

**踩到的两个坑（真调 API 才发现）：**

1. `thinking` 是 DeepSeek 私有扩展，openai SDK 不接受标准之外的关键字参数，必须走 `extra_body`（SDK 会合并进请求体顶层）。

2. ★ **V4 默认开启思考模式，必须显式传 `{"type":"disabled"}` 关掉。**
   同一问题实测：不传 88 output tokens、显式 disabled 只要 50 —— **白花 76%**。
   平台里绝大多数调用（分类、改写、格式化、抽取）不需要思考，一律关掉。
   |            | output tokens | 推理字数 | 正文字数 |
   |---|---|---|---|
   | 不传 thinking | 88 | 106 | 69 |
   | **显式 disabled** | **50** | **0** | 90 |
   | enabled + low | 101 | 219 | 61 |
   | enabled + high | 90 | 115 | 60 |

3. **推理 token 占输出配额**：`max_tokens` 给小了会被推理吃光、**正文返回空串**（`finish_reason=length`）。
   这是静默失败，适配器已加 WARNING 告警。开思考时 `max_tokens` 至少给 1500。
   （这个坑你的 RAG 项目 HANDOFF 里也记过，同一个成因）

**待你补的一步**：在 `backend/.env` 填 `LFP_DEEPSEEK_API_KEY`。
未填时设 `LFP_MODEL_BACKEND=fake` 可无 key 开发与跑 CI。

- **可并行**：RAG 侧的 R1–R3（升 3.12 + 换 DeepSeek + HTTP 薄壳），不依赖任何业务模块，做完就能让律师先用裸检索界面收集反馈，**风险前移**

**① 把自己关在门外，且没有钥匙。**

**② 检索一次，历史里冒出五条。**
`run()` 的闸门写的是 `if (busy) return`，但 `busy` 是 React state ——
要等下一次渲染才为 `true`。连按回车（或按住回车触发自动重复）时，
几个回调看到的都还是旧的 `false`，于是同一个问题被提交好几次。
实测数据：`search_log` 第 127–131 条是同一个问题，其中三条在 1.2 秒内。

修法：改用**同步的 `useRef`** 当闸门，并在回车处理里忽略 `e.repeat`。
利冲面板的「跑检查」「放行」是同一个毛病 —— 重复放行会重复设墙、重复写审计，
一并按同样的方式修掉。

> **写给以后的自己**：凡是"点一下会产生一条记录"的按钮，
> 防重复必须用 `useRef`，不能用 `useState`。state 的闸门永远慢一拍。

**注意一个正常行为，别当 bug：** 对已经在办的案件重跑利冲，会生成一条新的
`pending` 检查，但**不会把案件状态退回去**。在办案件不该被一次重跑自动叫停 ——
面板会把「待管委会决定」显著标出，由人来决定要不要终止。

**踩到并修掉的两个坑**

**① checkpoint 表会掉进 public。**
`PostgresSaver.setup()` 建的是不带 schema 前缀的表，落在 `search_path` 第一个 schema。
不钉死就掉进 public —— 「每个模块独占一个 schema」这条铁律直接破功，
`db purge workflow` 也清不干净。修法：连接串上钉
`options=-csearch_path%3Dworkflow`。测试 `test_checkpoint_tables_live_in_workflow_schema` 钉死。

**顺带的迁移陷阱**：这四张表不在我们的 ORM metadata 里，autogenerate
一看见就会判成"库里有、代码里没有" → 生成 `op.drop_table('checkpoints')`，
**等于把全所在跑的案件流程一次抹掉**（Step 1 踩过同款，当时差点 drop 掉
`kernel.module_state`）。已在 `env.py` 加 `ENGINE_OWNED_TABLES` 白名单，
并实测第二次 autogenerate 产出空迁移、零 drop。

> 为什么不给它们写 ORM 模型：结构由 langgraph 决定、随版本变，
> 我们写一份就等于跟库的迁移打架。让库自己管，我们只负责别删它。

**② `db purge` 拆得掉、装不回来。**（本步最值钱的发现）

`purge_module` 从**文件名**猜 revision：`stem.split("_")[0] + "_" + stem.split("_")[1]`。
对手写的 `hello_0001_init.py` 恰好蒙对（revision 真叫 `hello_0001`），
但 alembic 自动生成的 `6d1af4734562_workflow_runs_and_steps.py` 会被猜成
`6d1af4734562_workflow` —— **一条版本记录都删不掉**。

后果隐蔽且致命：schema 被 DROP 了，版本记录还在，
`db upgrade` 于是认为"早升过了"直接跳过 —— 模块拆得掉、**装不回来**。
「每个结构互相独立、可拆卸」这条铁律实际是破的，而且从 Step 1 起就破着，
只因为一直只拆 hello 才没暴露。

修法：`_revisions_in()` 从文件里正则读出真实 revision（兼容
`revision = "x"` 与 `revision: str = "x"` 两种写法）。
回归测试 `test_purge_reads_real_revision_ids`。
实测 purge → upgrade 完整一轮：版本记录被正确删除、表被重新建出。

> **教训**：验收标准里写「删掉模块后系统正常」是不够的，
> 必须写「**删掉再装回来**后系统正常」。只验证前半程，
> 会让一个把模块变成一次性的 bug 活很久。

**为什么从劳动争议改成建工（2026-08-25 改）**

原方案定的是劳动争议，理由是法定时限最硬（仲裁时效 1 年、仲裁前置、
收到裁决 15 日内起诉）、量大、标准化，适合展示"流程驱动"。
**那是在语料存在之前定的，纸上谈兵。** 开做前查了库，结论相反：

| | 法条 | 判例（标题粗分） |
|---|---|---|
| 建设工程 | **14 部** | **83 篇** |
| 劳动争议 | **0 部** | 66 篇（且多为"治理欠薪"，实为建工农民工工资） |

《劳动法》《劳动合同法》《劳动争议调解仲裁法》《工伤保险条例》**一部都没有**。

劳动争议流程跑起来会是这样：算仲裁时效 —— 无《调解仲裁法》第 27 条可引；
判经济补偿 —— 无《劳动合同法》第 46、47 条可引。只能拿判例说话，
或者靠模型记忆编条号，**Step 8 的引用校验节点会疯狂报警**。
而本平台的核心主张是"引用留痕、敢签字" —— 这恰恰是最不该拿来演示的东西。

建工侧的骨架同样够硬，足以撑起一条流程：

- **工程款优先受偿权 6 个月行使期限**（法释〔2002〕16 号 + 建工解释一第 41 条）
  —— 比劳动仲裁时效更要命，过期直接丧失优先权
- 竣工验收 / 结算 / 逾期不答复视为认可（解释一第 21 条）
- 黑白合同、招投标（招标投标法 + 解释一第 2、23 条）
- 工程造价司法鉴定程序、质量责任与保修期

且演示数据本就是建工（AJ2026001），Step 8 实测的"完工未验收但已实际使用
能否主张工程款"4 条引用全部命中、引用校验 0 告警 —— **这条线已被验证能跑通。**

> **教训**：业务线选题要由**语料**决定，不由题材的"典型性"决定。
> 劳动争议要做，得先补 5 部法条（劳动法、劳动合同法、劳动争议调解仲裁法、
> 工伤保险条例、劳动争议司法解释一），归入 Step 8.5。

**修掉三个真问题**

**① 状态在图里被整个替换掉了。**
`StateGraph(dict)` 用普通 dict 当 schema 时，LangGraph 把整个 dict 当**一个**通道，
默认 reducer 是"后者覆盖前者" —— 每个节点的返回值会把上一步的 state 整个冲掉。
实测：起点传进去的 `facts` 跑完第一个节点就没了，律师确认写回的 `confirmed` 也留不下。
**这种丢法极隐蔽**：`trail` 因为每个节点都读了再写，看起来一直是对的。
修法：业务状态整个塞进一个通道，给它一条合并 reducer（`GraphState`）。
Step 9 原来用 TypedDict 所以没暴露，Step 10 改成通用模板时才引入 ——
是 Step 9 的 `test_resume_finishes_the_flow` 把它逮住的。

**② `interrupt()` 会让整个节点重跑。**
它不是"就地挂起"：恢复时**节点函数从头再执行一遍**，`interrupt()` 那行才返回答复。
run 和 ask 塞进同一个节点的话，抽要素会多花一次钱、检索多跑一轮。
靠"跑过就跳过"的标记挡不住 —— 标记本身也是返回值，节点没跑完就中断了，
标记压根没写进 state。修法：编译时把一个 Step 拆成两个节点。

**③ 开思考时推理 token 吃光输出配额，正文返回空串。**
实测同一份意见书提示词：`max_tokens=4000` 时推理占满 4000、正文 **0 字**；
给到 8000 才正常吐出 1994 字。当时流程把空串当成正常草稿，
问律师"已生成（0 字），请确认" —— 比报错还糟，律师会以为模型认为无话可说。
修法：配额提到 8000，且**空正文一律报成错误**。

> **教训**：凡是"外部返回空值"的路径，默认都要当异常处理。
> 静默的空结果比报错危险 —— 报错律师会来问，空结果他会当成结论。

**顺带修好的记账**：适配器按美元记账（`cost_usd`，厂商就是这么报价），
流程里却按 `usage["cny"]` 取 —— 键名对不上，花费**静默变成 0**。
汇率现在只在 `settings.usd_cny_rate` 一处定义。

**推进改成后台线程**：一趟几十秒，同步 HTTP 会把请求吊死
（和 Step 8 给检索做任务化同一个理由）。`start`/`resume` 立刻返回 `running`，
前端轮询。`LFP_WORKFLOW_ASYNC=false` 切回同步，单测走这条路 ——
测试用的 session 活在一个最后会回滚的事务里，后台线程那条连接看不见它。

踩到的配套坑：`live_state()` 在后台线程还没写下第一个 checkpoint 时读到**空快照**，
把它当成"跑完了"，反手把业务表状态改成 `done`。修法两处：
空快照判为 `running`；`live_state` 在 `running` 时不回写（状态归线程管）。

**前端**：`components/WorkflowPanel.tsx`，排在检索面板**之前** ——
流程会自己把该查的查了，下面那个搜索框留给"流程没覆盖到的临时一问"。
界面顺序刻意固定为：① 时限（红的，带法条依据）→ ② 争议焦点与依据
（显示"它替你搜了什么"，否则律师无法复核）→ ③ 轮到你确认（能改机器抽错的东西）。

**已知欠账**

- 只有承包人/发包人两个视角，分包、实际施工人视角的规则还没细分
- 流程是线性的，没有分支。真实案件会有"要不要申请鉴定"这类岔路 —— 留白，别提前做
- 意见书只生成不落库。Step 11（doc）和 Step 12（draft）接手后要能存成文档、能改

**前端翻的一次大车：无限重渲染（2026-08-26）**

现象：页面肉眼可见地闪，案件页、检索、流程**同时**报"连不上后端"。
而服务端怎么测都正常 —— 直连 200、走代理 200、连打 20 次 0 失败。

根因在 `useNotice()`：它每次渲染都返回**全新的函数**。
`WorkflowPanel` 把 `clear`/`fail` 写进了 useCallback / useEffect 的依赖，
于是依赖每次渲染都在变 → effect 每次渲染都重跑 → 里面 setState → 再渲染，
**无限循环**。每秒几百个请求把 dev server 的代理冲垮，所有面板一起挂。

★ **`tsc` 和 `next build` 都查不出来** —— 类型全对，构建全过，只有跑起来才炸。
反向验证时更直接：退回旧写法跑测试，Node 直接
`JavaScript heap out of memory`。

修了三处：

1. `lib/notice.ts`（从 ui.tsx 拆出来，因为要能被 Node 直接测）——
   三个函数 `useCallback`，返回值 `useMemo`。**身份稳定不是优化，是正确性要求。**
2. 轮询容错：原来"一次失败即 stopPolling + fail"，一次抖动就把轮询永久停掉、
   红横幅永久留屏，服务恢复了也不会自愈。改成连续失败 3 次才认输、一成功就清横幅。
   检索面板的问答轮询同款毛病，一并修。
3. `Failed to fetch` 换成能照做的提示（哪个服务没起、该跑哪条命令）。

**前端从此有测试了**：`npm test` → `tests/notice.test.mjs`，
jsdom + 真 React + 真 effect。反向验证过：坏版本 3 条全挂并给出人话原因。

> **教训**：前端只有 tsc 和 build 是不够的 —— 它们看不见运行时的循环。
> 凡是自定义 hook 返回函数，身份必须稳定；凡是后台轮询，一次失败不能判死。

#### ✅ Step 11 — `doc` 文档管理 【已完成 2026-08-26】

- **产出**：上传、案件文件夹、版本、全文检索（走 `StoragePort`）

**Step 11 落地记录（2026-08-26）**

**两张表，分工是刻意的**

    document          文档的**身份**：属于哪个案子、放哪个卷宗、叫什么
    document_version  **每一版**：对象存储的键、大小、指纹、抽出来的正文

律所的文书是反复改的。「起诉状」从头到尾是同一份文档，但它有 v1/v2/v3。
**版本行只增不改** —— 改了旧版本，就答不出「我们当时递上去的是哪一版」，
而这个问题在纠纷里是要命的。

文件本体进 MinIO（走 Step 2 就建好的 `StoragePort`），库里只留元数据和正文。

**三条底线**

1. **权限跟着案件走。** 每个入口都过 `case_api.assert_visible` ——
   数据范围和隔离墙已经在那儿实现好了，绝不另起一套。实测：李明能看
   AJ2026001 的案卷（3 份），看 AJ2026003 直接被隔离墙拒掉。
2. **删除是软删。** 谁在什么时候删了什么，合规要问；物理删就答不上来。
   对象存储里的文件也留着 —— 存储便宜，答不上话很贵。
3. **下载走后端转发，不发预签名链接。** 预签名 URL 发出去之后，
   在有效期内谁拿到谁能看 —— 案卷材料受保密义务约束，不能让一条链接
   绕过权限体系。走后端还能把每次下载记进审计。代价是带宽，值得付。

**★ 这个模块最要紧的东西：说清楚哪些文件搜不到**

律所案卷里全是**扫描件** —— 法院送达的裁定书、对方寄来的证据，
扫成 PDF 之后一个字符都没有，只有图。

如果这种文件被静默记成「正文为空」，律师搜「裁定书」搜不到时，
会以为**案卷里没有这份材料** —— 但它明明躺在那儿。
**搜不到比搜错更危险，因为搜不到不会引起怀疑。**

所以抽取结果分四种状态，界面上单独有一块列出搜不到的文件：

| 状态 | 含义 |
|---|---|
| `ok` | 抽到正文，全文检索能命中 |
| `empty` | 文件里没有文字层 —— **多半是扫描件**，要 OCR |
| `unsupported` | 图片/压缩包/音视频，本来就不解析 |
| `failed` | 加密或损坏 |

OCR 现在不做（要装 tesseract 或调云服务，另一个量级）。**不做可以，
但必须让律师知道这份文件搜不到。**

**中文全文检索用 pg_trgm，不是 to_tsvector**

Postgres 自带的分词器**不认识中文**：`to_tsvector('simple','建设工程施工合同')`
把整句当成一个词，搜「施工合同」一条都搜不到。要正经分词得装
zhparser / pg_jieba（额外扩展、要编译），我们选按子串搜，
用 `GIN + gin_trgm_ops` 索引撑速度。实测「优先受偿权」「擅自使用」
「竣工验收」都能命中并给出上下文片段。

**接上了 Step 10：意见书自动归档**

流程**终审通过之后**（不是起草之后）把意见书存进案卷「法律意见」。
走**可选依赖** —— 没装 doc 模块流程照样跑完，只是不归档。

实测：一条完整建工流程跑完 → 文档 #94 → 在案卷里搜「优先受偿权」
同时命中意见书和起诉状。**Step 10 那份意见书终于存得下来了。**

**修掉两个问题（都在真实运行里暴露）**

**① 起草空正文，8000 配额还是不够。**
开着思考时**推理 token 也吃输出配额，而它吃多少不可预测**：
同一份提示词这次 8000 够、下次就不够（实测两次都撞上）。
靠调大配额只是把墙往后挪。

改成**降级重试**：空正文就关掉思考再跑一次。起草本质是
「把给定材料组织成文」，资料都在提示词里，不开思考照样写得出来 ——
质量略降，比交一份空白强得多。降级生成的稿子会在确认页标出来，
律师有权知道这一版是怎么来的。

**第一次真实运行就用上了**：开思考那次返回空，关掉后写出 2627 字。

**② 草稿为空时归档静默跳过。**
`archive_note` 是 `None`，什么都不说 —— 这正是本项目一再吃亏的那类错，
**空结果不会引起怀疑**。改成明确写出「草稿为空，没有可归档的内容（原因）」。

> 讽刺的是这条教训我在 Step 10 刚写进手册，转头自己又犯了一次。
> 所以现在有测试钉着：`test_nothing_to_archive_says_so`。

**权限**：`doc.view` / `doc.upload` / `doc.manage` / `doc.delete`。
律师能传能改，**不给 `doc.delete`** —— 案卷材料删不得，
要删由团队负责人判断（而且只是软删，本体还在）。

**已知欠账**

- **没有 OCR** —— 扫描件搜不到，只能靠人翻。这是最该补的一块
- 没有在线预览，只能下载

#### ✅ Step 12 — `draft` 文书生成 【已完成 2026-08-26】

- **产出**：文书模板 + DeepSeek 生成 + 结构化输出
- **坑**：复用 RAG 已有的防幻觉提示词思路（只用参考资料、每个论断带编号）

**Step 12 落地记录（2026-08-26）**

**这一步最重要的判断：哪些内容绝不让模型写**

一份起诉状里，当事人名称、住所、法院名称、诉讼标的额 —— 这些都是
**案件数据**，平台里本来就有。让模型去「生成」它们，等于让它照上下文
猜一个名字。猜错一个字，立案窗口就退回；猜错金额，诉请就废了。

所以每一节标明来路：

| 来路 | 含义 | 起诉状里的例子 |
|---|---|---|
| `fill` | 从案件/案卷直接填，**不过模型** | 原告、被告、此致（法院）、证据清单 |
| `generate` | 要论述，交给模型，只能引给定依据 | 诉讼请求、事实与理由 |
| `manual` | 律师自己写 | 具状人与日期 |

实测：建一份起诉状骨架，**一次模型都不调**，当事人、法院、
证据清单（取自案卷「证据材料」）当场就填好了。
**这不是省钱，是准确性问题。**

**四个模板**：民事起诉状、民事答辩状、律师函、法律意见书。

**★ 防幻觉靠校验，不靠祈祷**

提示词里写「只能引用给定依据」是必要的，但那只是**请求**。
真正管用的是生成之后**逐个核对**：文里每一个【S数字】，
是不是真的在给它的依据清单里？

`verify_citations()` 报三种事：

1. **引了不存在的编号** —— 只给了 S1–S8 却写了【S13】。**这就是编的**
2. **一条依据都没引** —— 论述型段落不给依据，等于凭空说话
3. **引到已废止/失效的条文** —— 内容对得上，但不能用了

**定稿时硬拦第一种。** 实测：手工塞一个【S13】进去，
定稿直接被拒并指名道姓：「引用了不存在的依据编号 S13 —— 手里只有 S1–S8，
**这些是编的**」。改回来之后才放行、归档。

> 这是「敢签字」的底线。带编造条号的文书递出去是执业事故。

**按节存，不按整篇存**

律师改完「事实与理由」，想重新生成「诉讼请求」—— 如果整篇是一个字段，
重生成就把他改过的东西冲掉了。按节存就能只重跑一节。

而且**律师亲手改过的段落，重新生成会先拦一下**，要显式确认才覆盖。
辛苦改完被一键重生成冲掉，是最让人火大的那种 bug。

**接上了 Step 11**：定稿即归档进案卷（起诉状进「诉讼文书」，
意见书进「法律意见」），随即可被全文检索命中。
实测跑完：文书 #99 → 案卷文档 #190 → 搜「优先受偿」命中。

**起草一律不开思考。** Step 10 两次栽在「推理吃光输出配额、正文返回空串」上。
起草是「把给定材料组织成文」，材料都在提示词里，这是组织语言不是推理。
实测一份起诉状两节生成花 ¥0.008。

**真实运行里修掉的两个瑕疵**

**① 当事人印成了 `plaintiff`。**
库里存英文枚举是对的（稳定、好比对），但**落到纸上必须是中文**。
一份写着「宏远建设集团有限公司（plaintiff）」的起诉状是递不出去的。

**② 「诉讼请求」被报「没有引用任何依据」。**
那是请求清单，本来就不引法条。给它报告警是**噪音**——
而噪音会让人开始忽略告警，等真的编造出现时也一起忽略掉。
加了 `needs_citation` 标记，只对要讲法律道理的段落要求引用。
**但「不要求引用」≠「允许编造」** —— 编号造假照抓不误，有测试钉着。

**权限**：`draft.view` / `draft.create` / `draft.finalize`。
律师三个都有 —— **文书是他签字的东西，定稿本来就该由承办律师做**，
不是找人代批。

**Step 13 落地记录（2026-08-26）· 阶段四收官**

**独立成模块，不是塞进 draft**

`citation` 有自己的 schema，通过一对**不透明标识** `(doc_kind, doc_id)`
挂靠文书 —— 不跨 schema 建外键。理由有二：铁律是每个模块独占一个 schema，
跨库外键会把两个模块焊死；而且这样将来 workflow 的意见书也能挂进来，
不用改一行。

两张表：

    citation   一条依据在某份文书里的**快照**
    anchor     这条依据的每一次出现，精确到字符区间和所在句子

**★ 快照要存全，因为检索库会重建**

Step 8 就定过：库会换数据源、重新切分、扩充法条。重建之后 chunk_id 全变，
条文也可能改版。如果这里只存一个 source_id，半年后律师点开文书里的【S3】，
看到的可能是**另一条内容**，甚至什么都没有 —— 而这份文书已经递出去了。

所以存下当时的：原文片段、时效状态、**语料版本指纹**、**检索 trace_id**、
以及「为什么查它」。库怎么变，这份文书的引用都还原得回来。

**★ 锚点是推导的，不是维护的**

位置来源就是正文里的【S3】这个标记本身，正文一变就整段重算 ——
**偏移量永远不会漂**。手工维护偏移量的方案在第一次编辑之后就全错了。

实测：在句子前面插一大段前言，锚点仍然精确指在「被告擅自使用【S1】」上。
有测试钉着（`test_anchors_do_not_drift_after_editing`）。

**★ 引用标记原位渲染，不剥掉再补到句末**

「根据【S1】，建设工程未经竣工验收…」如果把标记剥掉再把编号补到句末，
就读成「根据，建设工程未经竣工验收…」—— 标记本来夹在「根据」和逗号之间。
律师读的是**这句话本身**，不能为了标注方便把它读乱。
所以接口返回 `segments`：`[{t:"根据"}, {cite:1}, {t:"，建设工程…"}]`。

#### ✅ Step 14 — `task` 任务 【已完成 2026-08-27】
#### ✅ Step 15 — 时限引擎 ★ 【已完成 2026-08-27】

两步**合成一个 `task` 模块**做的。理由：待办和时限在律师眼里是同一件事
（「这周我要做什么」＝任务 ＋ 快到期的时限），拆成两个模块会立刻需要
一个跨模块的合并查询，那是把一件事切开再缝上。

**三张表**（`task` schema，独立 Alembic 分支 `c78f1e0bc816`）

| 表 | 是什么 | 关键点 |
|---|---|---|
| `deadline_rule` | 时限**规则** | ★ 规则是**数据不是代码**，律所自己加，加一条不用发版 |
| `deadline` | 某个案子的某条时限 | 规则算出来的骨架 + 律师确认过的事实 |
| `task` | 待办事项 | 可以挂在时限上（`deadline_id`），也可以独立 |

**10 条内置规则**（`modules/task/rules.py`）：工程价款优先受偿权（6 个月，
除斥）、建设工程/普通诉讼时效（3 年）、竣工结算答复期（28 天）、地基与主体
质量责任（无固定期间）、一审判决/裁定上诉期（15/10 日，除斥）、申请强制执行
（2 年）、劳动仲裁时效（1 年）、不服裁决起诉期（15 日，除斥）。

**四个设计决定，每个都是为了防同一类事故：假的安全感**

1. **算不出就说算不出，而且点名缺哪个日期。**
   缺起算日的时限状态是 `unknown`，界面显示「缺『竣工验收日期』」而不是
   一句「算不出」，更不是留空。留空会被读成「没事」—— 一个律师如果以为
   系统在替他盯着，而系统其实什么都没盯，这比没有系统更危险。

2. **「没有固定期间」和「算不出」是两个状态。**
   质量责任是「设计使用年限内」，没有可加的期间。第一版把它也标成
   `unknown`，后果是律师把竣工日期老实填进去 —— 它**还是**红的。一条永远
   变不成绿色的红字，两周内就会被无视，然后旁边真正致命的「算不出」跟着
   一起被无视。**假警报会吃掉真警报。** 所以它有自己的状态 `no_fixed`：
   显示，但不催，也不进看板的红色计数。

3. **除斥期间不许中断 —— 界面上根本不出现那个按钮。**
   不是「禁用」，是不渲染，外加一句说明。禁用的按钮会让人以为
   「权限够的人就能点」，而这是法律性质，跟权限无关。
   后端同样硬拦（`task.not_suspendable`），不靠前端自觉。

4. **拒绝中断的三种理由，分开说。**
   ① 除斥期间（法律性质）② 没有固定期间（没有可重新起算的东西）
   ③ 本所规则没标可中断（这是配置，去改规则）。第一版三种共用一句
   「是除斥期间」，等于**在界面上讲错法律** —— 律师会照着这句话理解
   一条期限的性质。能不能中断由后端 `can_interrupt` 说了算，界面不按
   `fatal` 自己猜；不能中断的连按钮都不渲染，并说明是哪一种。

5. **每条规则自带 `caveat`，说清它**盖不住**什么。**
   例：上诉期那条写着「从收到判决书之**次日**起算，不是判决日期；涉外
   当事人在国外的是 30 日」。提示不是承诺 —— 规则表是律所维护的，系统
   只做算术，判断仍然是律师的。

**权限**：`task.view` / `task.manage` / `task.deadline` / `task.manage_rule`。
★ 律师**不给** `task.manage_rule` —— 时限规则是全所统一口径，一个人改了
所有人跟着变；管委会和团队负责人才能改。

**起算字段是封闭词表**（`payable_on` / `completed_on` / `handover_on` /
`settled_on` / `served_on` / `known_on` / `effective_on`）。律所自建规则只能
从这里选，理由有两个：① `generate()` 只从流程抽出的要素里按这些字段名取值，
写一个没人填的字段名等于造了一条**永远停在「算不出」的僵尸规则**；
② 词表外的字段没有中文名，界面会显示成「缺『anchor_x』」，等于没提示。

**和流程接上了**：`workflow` 的 `_deadlines` 步骤通过
`registry.optional_api("task")` 调 `task.generate()`，把流程抽出来的要素
（竣工日期、应付款日期……）直接落成时限。这补上了之前一个真实的设计缺口 ——
**流程抽出的要素从来没写回案件**，跑完就散了。
用 `optional_api` 而不是硬依赖：没装 task 模块时流程照跑，只是不生成时限。

**重新生成不覆盖人工判断**：`generate()` 跳过 `confirmed_at` 或
`interrupted_on` 非空的行。律师定过的起算日，规则再跑一百遍也不动。

**界面**
- 案件页 `TaskPanel`：时限清单 + 本案待办。位置在文书之后、案卷之前 ——
  它得在流程下游（要素先抽出来），但又必须在律师往下翻之前撞见。
- `/todo` 看板：按「离出事有多近」排序 —— 已过期 → 算不出 → 临近 → 正常。
  ★ 「算不出」排在「临近」前面是刻意的：临近的至少系统在盯，算不出的
  **没人在盯**。
- 顺带修了 `/cases?id=N` 深链（看板每行都指向一个案件，点进去只回列表
  等于没链接），以及后端文案里的 `**加粗**` 在前端被原样打印的问题。

**验收**：`pytest -q` 342 passed；`kernel.cli check` 边界通过；
端到端脚本走真 HTTP + 真库，覆盖规则灌入幂等、权限拒绝、生成、确认起算日、
重新生成不覆盖、除斥期间拒绝中断、普通时效中断后顺延、任务与看板 —— 全绿，
且可重复跑（脚本自建案件，不动演示数据）。

**中断 / 中止 / 最长保护期**（2026-08-27 补齐，迁自 RAG 的时效工具，见 C4）

| | 依据 | 算法 | 界面 |
|---|---|---|---|
| 中断 | 195 条 | 自中断之日**重新起算**整个期间 | 「登记中断」 |
| 中止 | 194 条 | 自障碍**消除**之日起满 **6 个月**届满 | 「登记中止」 |

★ **三者绝不合并成一个带参数的接口/下拉。** 中断把期限推得很远（整个

★ **最长保护期是这个引擎存在的理由。** 一个每年发一次催款函的案子，
每次中断都把届满日推后三年 —— 没有上限的话，系统会一路显示「正常」

补上（说明律所从没碰过它），不是默认值的一个字不动（那是律所的选择）。

| 逐级审批 | ❌ | 咨询是**已经发生的收费事实**，不需要"这 40 小时该不该报"的判断。加审批只会让人拖着不记 |
| 漏记反查 | ❌ | 那是为"每天必须记满"设计的。咨询没有这个前提 |
| 6 分钟取整 | **半小时** | 6 分钟制是计时律所为了把每一分钟都换成钱。咨询是"聊了一个多小时"这种粒度，报 1.3 小时只会让客户觉得你在抠 |
| 挂案件 | **挂客户，案件选填** | 多数咨询发生在立案之前甚至根本不立案。只能挂案件的话，"来聊一下、收 1500、没接案"这种最典型的情况记不进去 |

**保留的两条**（它们和计时制无关，是记账的基本要求）：

- **金额记录时算好钉死，不每次重算** —— 费率以后调价，去年那条咨询不该跟着变
- **出账后改不动** —— 已经报给客户的数字不能事后悄悄改，要改只能作废重记

**新增：不足 15 分钟不计费。** 见面寒暄二十分钟就开账单，客户不会有第二次。

**新增：免费咨询必须写原因。** 不写理由的免费，事后分不清是优惠还是漏收。

#### ✅ Step 17 — `billing` 账单 【已完成 2026-08-27】

- **产出**：五种收费模式、**风险代理合法性硬拦**、账单生成、回款登记、账龄

**五张表**（`billing` schema，独立迁移分支 `73ee3027fde8`）

| 表 | 是什么 | 关键点 |
|---|---|---|
| `fee_rate` | 本所按什么价卖时间 | 按**职级**定价，带生效期 |
| `engagement` | 这个案子怎么收 | 委托合同里的收费条款；**合法性在这一层拦** |
| `invoice` | 一张账单 | 金额算出来**存下来**，开出即锁死 |
| `invoice_line` | 账单的每一行 | 客户逐行看、逐行砍 |
| `payment` | 回款 | 钱到账才算收到 |

收费模式：计时 / 固定包干 / 风险代理 / 混合（基础费＋风险）/ 常年顾问费。

**★ 这个模块唯一不由律所说了算的部分：风险代理**

费率多少、打几折、分几期，都是律所的生意，系统不该有意见。但
「哪些案子不许风险代理」「最高收多少」是**规章定的**
（《律师服务收费管理办法》，发改价格〔2006〕611 号）：

| 档位 | 适用 | 处理 |
|---|---|---|
| `block` | 刑事、行政诉讼（第十二条）；比例超 30%（第十三条） | **直接拒绝**，报错带条文 |
| `confirm` | 劳动争议、民事大类（第十一条四类请求） | 写清禁区，律师确认后放行，**确认留痕** |
| `allow` | 未匹配 | 放行，但明说"不等于一定可以" |

★ **为什么劳动争议是 confirm 不是 block**：禁的是"请求支付劳动报酬"这个
**诉讼请求**，不是案由 —— 竞业限制补偿、违法解除赔偿金同样挂在劳动争议下，
并不当然禁止。系统看不到具体诉请，**这种情况下装作知道比不知道更危险**。

★ **确认要留痕**（`legality_note` + `confirmed_by/at`）：收费违规被查时，
"系统提示过、律师确认过"和"没人提过"是两种处境。

★ 界面上，选中「风险代理」的**当下**就弹提示，不等点保存 ——
律师需要拿这段话去跟客户解释为什么不能这么签。confirm 用黄框，
block 升级成红框并禁用保存按钮。

**钱的算术：四条不能错的**

1. **一律 Decimal / Numeric(18,2)。** 0.1+0.2≠0.3 落在律师费上，
   就是账单和收款差一分钱，然后财务花半天去找。
2. **ROUND_HALF_UP，不用银行家舍入。** 客户拿计算器按出来的是四舍五入，
   你没法跟他讲"0.125 舍成 0.12 是因为 2 是偶数"。
3. **代垫费用和律师费分开，且不计增值税。** 诉讼费、鉴定费是替客户垫的钱，
   原价转付。更要紧的是 —— **风险代理那 30% 的基数不含代垫费用**，
   混在一起算，上限就被撑大了，而撑大的方向永远是超收。
4. **合计严格等于分项之和。** 客户一加发现总数对不上分项，整张账单的
   可信度就没了。所以税额用「含税−不含税」反推，不是「不含税×税率」直算。

**含税 / 不含税必须明确写死** —— 这是中国律所收费纠纷的前三名：
口头谈的时候谁也没说，开票的时候差 6%，两边都觉得对方赖账。
`tax_included` 是必填项，界面上一直显示着。

**和 time 接上了**：`pull_time()` 通过 `time.billable_entries()` 拿工时，
账单行**直接用工时的工作说明** —— 那句话本来就是写给客户读的。
开出账单时调 `time.mark_billed()` 把工时锁死。

★ **草稿阶段不锁工时**：草稿还会加加减减，那时候就锁，等于用户删掉
一行之后那条工时再也回不来了。

★ **没有费率的人，整个动作失败并点名是谁**，不按 0 算过去 ——
按 0 算出来的账单看着很正常，然后所里少收一个人的钱，
**而这种错没人会发现**，因为那几行确实存在，只是金额是 0。

**权限：三件事各有各的把关人**

| 角色 | 谈收费 | 开账单 | 收款 | 费率 |
|---|---|---|---|---|
| 管委会 | ✓ | ✓ | ✓ | ✓ |
| 团队负责人 | ✓ | ✗ | ✗ | ✓ |
| 律师 | ✗ | ✗ | ✗ | ✗（只看自己案子） |
| 财务 | **✗** | ✓ | ✓ | ✓ |

★ 业务口**不给 issue/payment**：业务口开单、业务口销账，就没有第二双眼睛了。
★ 财务**不给 manage**：收费怎么谈是业务的事，财务改了约定就说不清是谁答应客户的。

**开发中修掉的问题**

1. **补权脚本被自己输入里的重复项弄崩了。** `GRANTS` 是手工拼的，
   同一个权限出现两次很正常 —— 一个补权脚本因为这个就崩掉是它自己的毛病。
   改成 `dict.fromkeys` 去重（既去重又保持打印顺序可读）。
2. **界面标题和后端 message 说了同一句话。** "这个案由部分禁止风险代理"
   连着出现两次，读的人会以为哪里出错了。改成 message 只放实质内容，
   引子由调用方按场景加 —— 报错那条路没有标题，引子在 service 里补。

**应收账款页**：主角是**账龄**不是总额。一笔挂了 200 天的应收和一笔上周
开的同额账单是两回事；只显示"应收合计 380 万"的看板，等于让一堆烂账
和一堆正常在途的钱长得一模一样。逐笔按账龄倒序 —— 催款就该按这个顺序打电话。

**验收**：`pytest -q` 443 passed（其中 billing 46 条）；`kernel.cli check`

#### ✅ Step 18 — `approval` 单据流转 【已完成 2026-08-27】

- **产出**：Ticket 单据模型、流转链（数据）、待办、请款/报销/用印/付款、回写账务

**三张表**（`approval` schema，迁移分支 `4b827e342332`）

| 表 | 是什么 |
|---|---|
| `flow_rule` | 什么单据、多少钱，走哪几道 —— 规则即数据 |
| `ticket` | 一张单子。★ **上面根本没有案情字段** |
| `ticket_step` | 走过/要走的每一道，链条在提交时固化 |

**★ 手册给这一步标的坑，就是这个模块存在的理由**

> 财务只看得到单据和金额，看不到案情 —— payload 只放财务需要的字段

律师提一张请款单，财务要付这笔钱。财务需要知道的是：多少钱、付给谁、
什么名目、谁批的。**不需要**知道这是哪个当事人、什么纠纷 ——
而律所里最敏感的东西恰恰是这些。

隔离靠**结构**不靠权限：ticket 上没有案情字段，只有 `subject`（一句话事由）
和金额。想看案情去案件页看，那受 `case.view` 管，是另一回事。

**结构隔离之后，剩下唯一的泄漏口是事由那一栏。** 律师顺手写成
「宏远诉凯达工程款纠纷的鉴定费」，隔离墙就白建了。所以有
`check_subject_leak()`：案件标题、当事人名字出现在事由或补充说明里，
直接拒绝并**给出改法**（「诉讼费垫付」「鉴定费垫付」）。
不是不信任律师，是这一栏太顺手了。

★ **只拦认得出来的。** 案由、争议焦点这些系统看不出，所以界面上
在律师**写的当下**就标着「这一栏财务、行政、用印管理都看得到」，
并给几个可以直接点的范例。拦截必然漏，漏掉的只能靠人自觉 ——
所以提示和拦截都要有。

★ **事由不从案件自动带出来。** 那是最省事、也最会泄漏的做法：
省下两秒钟，代价是每张单子都带着案由标题在所里流转。

★ **看不到的案件要明说，不能悄悄抹成 null。** 悄悄抹掉的后果是：
财务以为这单没挂案子，于是在备注里问「这是哪个案子的」，律师在备注里
答了 —— **隔离墙就从备注栏漏光了**。所以返回一句「本单关联了一个案件，
但你没有查看权限。★ 这不是错误」。界面上用中性灰蓝框，不用警告色 ——
做成红框黄框，人会当成故障去追。

**分权：批的人、付的人、盖章的人，是三个人**

| 角色 | 提单 | 团队这道 | 所级这道 | 付款 | 用印执行 |
|---|---|---|---|---|---|
| 律师 | ✓ | ✗ | ✗ | ✗ | ✗ |
| 团队负责人 | ✓ | ✓ | **✗** | ✗ | ✗ |
| 管委会 | ✓ | ✓ | ✓ | ✗ | ✗ |
| 财务 | ✗ | **✗** | ✗ | ✓ | ✗ |
| 行政 | ✓ | ✗ | ✗ | ✗ | ✓ |

★ 团队负责人不给所级审批：五千以上要过管委会，正是为了让第二个人看一眼；
两道权限给同一个人，两道就变成一道。
★ 财务**只付款不批单**：批的是"这钱该不该花"，付的是"钱确实出去了"。
同一个人既批又付，是所有财务内控的第一条红线。
★ 盖章的人不该是批准盖章的人。
★ 后端另有硬拦：**不能批自己提的单**。

**待办按权限算，不按指派** —— 指派到人的做法在律所里会卡住：负责人出差
三天，所有单子停摆。按权限走，有权限的人都能批，谁批的记在链上。

**用印是重管控**：章别、文件、申请份数都要填；执行时**必须回填实际盖了
几份**，超过申请份数直接拦 —— 申请 3 份盖了 5 份，那两份盖在什么上、
给了谁，事后查不清就是事故。

**回写账务（验收路径）**：请款单付完款 → 自动在 billing 挂一笔代垫 →
开票时 `pull_disbursements()` 拉进账单 → 开出时锁死。
为此给 billing 补了一张 `disbursement` 表（Step 17 只能开票时手工敲代垫，

★ 报销**不回写** —— 那是所里的成本不是垫给客户的钱，混进去客户会被

★ **原计划写的是「案由分布、人效、回款、时限达成率」，实际做的不是这个。**

### 创收有三个口径，混了就有人拿开票额去邀功

```
本期开票   开了账单 —— 不代表收到          ← 流量
本期回款   钱到账了 —— **律所说"创收"指这个**  ← 流量
未收       开了收不回来的                  ← 存量
已逾期     过了约定付款日还没收到的          ← 存量
```

★ **界面上流量和存量分两排摆。** 混在一排会出现
「本期开票 12 万、未收 23 万」这种看着矛盾的组合 ——
人一定看错，然后**不信任整个看板**。

★ 回款按**收款日**算，不按账单日。三月开的单五月收到，是五月的创收。

★ 创收按**主办律师**归集，界面上写明「案源分成还没做」——
否则案源律师会以为系统漏算了他。

### 架构：各模块自报，analytics 只汇总

```python
# manifest 里声明
metrics=(Metric(key="billing.received", name="本期回款", unit="money",
                scope_perm="billing.view", drill="/receivables"), ...)
# api.py 里实现
def metrics(session, principal, spec) -> dict
```

analytics 只做三件事：遍历、按权限筛、拼版面。
**加一个模块 = 看板自动多几个指标，analytics 一行不改。**

这是本项目**第四次**用这个模式（capabilities / archive_inventory /
archive_blockers / metrics）—— 已经是固定手法。

### 前端：OA 看板的几条经验

1. **按角色装配卡片，不是一个驾驶舱配权限开关。** 四种人关心的东西
   几乎不重叠，做成"大而全"每个人都要滚过 80% 不相关的。
2. **首屏只放"要我动手的"**，不放好看的统计。
3. **每个数字都能点开到明细** —— `Metric` 组件按 `drill` 渲染成链接。
   **点不开的数字是装饰**，看板的价值在于它是入口。
4. **列表 > 图表。** 管理者要的是"哪几个案子有问题"，不是分布饼图 ——
   饼图给感觉，列表给行动。全页唯一的图是案由分布条形（它表达的就是分布）。
5. **默认口径是本月**，不是"最近 30 天" —— 律所按月结算，
   跨两个结算月的数对不上任何一张月报表。
6. **拿不到就显示「查不到」，绝不显示 0。** 一个模块挂了显示
   「本月回款 ¥0」会吓死人，而且方向是反的。

★ **首页原本是 Step 3 的占位符**（写着"案件、任务、计时会陆续出现在这里"），
18 步没动过 —— 它占着最好的位置。Step 21 主要就是把它变成真的工作台。

### 小样本保护

团队 3 个人、总额已知，知道另外两个就能反推第三个 ——
**聚合数字看着无害，实际能反推到个人。**
所以人数 < 3 时只给总数不给分组，并说清为什么。

## 10. 附录：未来接 Agent（OpenClaw / 飞书 / 其他）

> **现在不做**，但 `capabilities` 声明与汇总已经在 Step 1 落地。这章写清将来怎么接。

### 10.1 OpenClaw 是什么

开源自托管 AI Agent（MIT，GitHub 68k star，PSPDFKit 创始人 Peter Steinberger 发起，2025-11 以 Clawdbot 之名发布）。四层 hub-and-spoke：

```
渠道适配器（飞书 / WhatsApp / Slack / Telegram…）
      ↓
Gateway 控制平面（常驻，路由消息 → agent 上下文）
      ↓
Agent 运行时
      ↓
工具执行（Skills + MCP servers + shell + 浏览器）
```

- **原生支持 MCP**（`@modelcontextprotocol/sdk`），`openclaw.json` 里加 `mcpServers` 块即可，JSON-RPC over stdio 或 HTTP
- **Skills** = Markdown 指令文件（塑造它怎么想）；**MCP** = 真正的外部工具调用
- 记忆是**本地 Markdown 文件**（local-first）

飞书接入两条路，都不需要公网 IP：
1. 内置飞书 channel（WebSocket 长连接）
2. 飞书官方插件 `larksuite/openclaw-lark` —— **OAuth 以用户本人身份操作**，覆盖消息/文档/多维表格/电子表格/日历/任务；要求 Node 22+、OpenClaw 2026.2.26+

### 10.2 接入形态

```
律师在飞书说"张三那个案子举证期限到了吗"
  → 飞书 channel → OpenClaw Gateway → Agent
  → MCP 调平台的能力出口 → task.listDue(case="张三…")
  → 结果发回飞书
```

平台侧只需要一个东西：**由 `capabilities` 自动生成的 MCP server**。声明方式（已实现）：

```python
# modules/task/manifest.py
from pydantic import BaseModel, Field
from kernel.manifest import Capability, ModuleManifest


class ListDueParams(BaseModel):
    case_id: str = Field(default="", description="限定案件，留空表示全部")
    within_days: int = Field(default=7, ge=1, le=90)


MANIFEST = ModuleManifest(
    name="task",
    requires=("case",),
    permissions=("task.view", "task.manage"),
    capabilities=(
        Capability(
            name="task.listDue",
            description="列出某案件或某人的临期任务",
            params=ListDueParams,
            requires_perm="task.view",
            read_only=True,        # 写操作必须显式 False，且要二次确认 + 审计
        ),
    ),
)
```

导出：`python -m kernel.cli capabilities --mcp` 直接得到 MCP tools 结构
（Pydantic 的 `model_json_schema()` 就是 `inputSchema`，零翻译成本）。

Agent **不 import 任何模块**，只从 Registry 拿能力清单。
**加模块 = Agent 自动多会几件事，Agent 侧代码一行不改。**

### 10.3 安全约束（律所场景，不可省）

OpenClaw 官方自己就警告：**幻觉、不可预测执行、提示注入**，建议"只做私人助手，别加进群"。放到律所更严重：

| 风险 | 对策 |
|---|---|
| **提示注入** —— 有人在飞书消息里塞指令，诱导 Agent 调接口翻案卷 | 平台 MCP server **独立鉴权**，不信任 Agent 声明的身份；token 绑定到具体律师，权限走 Step 4 的 `DataScope` |
| **越权** —— Agent 读到隔离墙案件 | 隔离墙案件**永不通过 MCP 出口暴露**，硬编码在出口层，优先级高于一切 DataScope |
| **写操作** —— Agent 自己建任务、发消息、改状态 | 默认 `read_only=True`（已有测试强制）；写操作要么二次确认，要么单独授权，**全部审计留痕** |
| **数据落地** —— OpenClaw 记忆是本地 Markdown，案情摘要会落盘 | 部署在**律所服务器**，不是律师个人电脑。写进部署规范 |

### 10.4 依赖风险

OpenClaw 创始人已加入 OpenAI（2026 年报道）。项目是 MIT 自托管，短期无碍，但**长期不要绑死它的私有 API** —— 始终只暴露标准 MCP 接口。换成任何别的 Agent，平台侧一行不改。

## 补做：归档 与 引用体检（2026-08-28 完成）

原来标为「待办 A / C」的两件，已做完。**B（结案小结）仍未做。**

### 归档 —— 新模块 `archive`（第 15 个模块）

**归档 = 三件事，缺一件都不算归了：**

| | 谁做 | 怎么做 |
|---|---|---|
| ① 拦住新的写入 | `case.assert_writable()` | 各模块写入口调它 |
| ② 编一份卷宗目录 | `archive` 模块 | 问遍 10 个模块「你这有几件」 |
| ③ 算指纹存下来 | `archive` 模块 | 将来能答「这卷被动过吗」 |

★ **为什么拆两半**：doc / time / billing / approval 全都依赖 case，
case 再去调它们就成环。所以**拦写留在 case**（大家本来就依赖它），
**编目录另开模块**（只调别人，没人调它）。

★ **归档前先检查有没有没了结的事**（`blockers`）。这一条是设计上最要紧的：
允许"先归档、再慢慢把工时审完"，就必须允许归档后写入 —— 那锁就形同虚设。
**反过来做才对：钱和活都清了才让归档**，于是锁可以是硬的。

★ **`force` 能跳过 blockers，但跳不过状态机。** 「必须已结案」是**硬前提**，
不是可强制的阻断项 —— 第一版把它放进 blockers，结果 force 一路放行、
建完归档记录，最后卡在 transition 上，**留下一条指向没归成档的孤儿记录**。

★ **归档必须能解档。** 案子会再审、会申请执行。原来状态机里
`"archived": ()` 是死路 —— 解档在状态机上根本走不通。
**没有解档，归档就是死胡同，然后没人敢归档，一个没人敢用的功能等于没做。**
现在 `"archived": ("closed",)`，只留这一个出口。

★ **不漏锁靠一条遍历测试**，不靠人记得：
`test_every_write_entry_point_is_blocked` 把 12 个写入口全试一遍。
以后新加模块忘了加锁，把入口补进那张表就会被抓出来。

★ **先推状态，再编目录。** 顺序反了指纹永远对不上 ——
「推到已归档」这个动作**自己会往状态流转记录加一条**。
而一个永远报警的校验，两天内就会被无视。

★ `skipped` 那一栏：装着却没报数的模块要**明说**。一个模块悄悄不参与，
卷就少一块，而**少的那块目录上根本不会出现**，没人会发现。

**实测**：演示案件 AJ2026001 编出 **56 件、零跳过**，扫描件在目录上单独标注
（「其中 2 件搜不到正文」）。

### 引用体检 —— `citation.recheck()`

`citation` 一直存着 `source_id` / `corpus_version` / `snippet` / `effective_status`，
**但在这之前没有任何一处拿它们和库比对过** —— 所以法条改了、废止了，
系统一声不吭。

做法：拿每条引用的 `source_id` 回 RAG 服务查现状，比对。四种结论：

| 结论 | 含义 |
|---|---|
| 未变化 | 库里和当时一致 |
| 原文已改动 | 同文号被修订 —— **两边原文并排显示** |
| 已失效 | 库里标了失效依据 |
| 库里找不到 | 退回显示当时冻结的 `snippet`（这是当初冻结它的全部理由） |
| 查不了 | 检索服务不可用 —— **明说，不假装没问题** |

★ **只报告不改。** 自动替换成新法条更危险 ——
律师会以为**还是他核过的那句**，而实际上换了。

★ **定稿时自动跑一次**，结论存进 `draft.recheck_note` ——
事后能证明"定稿那一刻提示过什么"。但**只警告不拦截**：
编造条号是律师的错必须拦；法条被修订是外面的世界变了，
律师完全可能明知而仍按行为时法引旧版。

★ RAG 侧新增只读接口 `POST /lookup`（`src/lookup.py`）。
法条按 `文号#条号` 反查，判例按案例号。

**实测**：演示文书查出 **2 未变 / 3 原文改动 / 1 库里找不到**。

### 这一轮修掉的问题

1. **`workflow_template` 是死数据**（见文档审计记录），顺带修了。
2. **一条绿着的、断言假话的测试**（同上）。
3. **测试污染全局容器** —— `test_workflow.py` 的 autouse fixture 绑了
   adapters 不还原，加校验时一次炸出 300+ error。
4. **财务开不出含工时的账单** —— `time.mark_billed` 要 `time.approve`，
   而财务被刻意不给。**错在那道检查越权了**：「谁可以出账」是 billing
   的判断，不是 time 的。改成要 `time.view_all`。
5. **换文书后引用体检不刷新** —— 会把上一份的"全部未变"显示给这一份。
   **一个显示错结论的体检，比不体检危险得多。**
6. RetrievalPort 加了 `lookup` 后 fake 适配器没跟上 ——
   `test_adapter_satisfies_both_ports` 当场抓住，那条测试值回票价。

"不能再新增事项"**一条，其余全都还能动：

| 归档后 | 现状 |
|---|---|
| 传/删案卷材料 | ❌ 能 —— `doc` 模块里没有一行和归档相关的代码 |

★ 这是**合规要求**不是锦上添花 —— 司法部对律师业务档案有专门的
立卷归档要求，律所要能拿得出完整的卷。

### B. 结案小结（一个字段）

Step 20 知识沉淀已确认推后，理由成立：**原材料一样不丢**
（案卷、文书、检索记录、引用快照都永久保存），晚三年抽和现在抽一样。

★ **但有一样东西会随时间流失**：「我们当初为什么这么打」——
选了哪个策略、放弃了哪个、对方为什么松口、法官庭上说了什么。
这些**不在案卷里，在人脑子里**。半年后人忘了，两年后人可能离职了。

补法成本几乎为零：结案时一个文本框，问三句话
（怎么解决的 / 值得借鉴什么 / 有什么坑要提醒后面的人），
存进 case 一个字段。**Step 20 将来抽的时候，这段话比整本案卷都值钱。**

### ~~C. 引用体检~~ ✅ 2026-08-28 已做

`citation` 存了 `corpus_version`、`effective_status`、`snippet`，
**但没有任何一处拿它们做比对** —— 所以**法条改了，系统不会告诉你**。

实际后果：一份在草稿箱躺了三个月的起诉状，期间司法解释修订了，
律师递上去还是老版本。

补法：拿 `source_id` 去问 RAG 服务当前是什么版本，和存下来的比。
变了就在文书上标一句「⚠ 这条依据可能已更新，定稿前请复核」。

★ **提示，不自动改。** 自动替换成新法条更危险 ——
律师会以为还是他核过的那句。

★ 顺带记清楚三种"法条更新"的区别（查证过 RAG 侧的 `stable_source_id`，
法条的稳定标识是**文号+条号**，如 `法释〔2020〕25号#第十四条`）：

| 情况 | 旧引用还指得到吗 |
|---|---|
| 出了新文号的司法解释（最常见） | ✓ 两条各在库里，互不影响 |
| 法条被废止 | ✓ 还在库里，标着"已失效" |
| **同一文号内容被修订** | ✗ 库里只剩新的，**旧原文只在 `snippet` 快照里** |

第三种是当初冻结 `snippet` 的全部理由 —— 它是唯一的退路。

## 试用回归（2026-08-28）

★ **这一节和上面所有 Step 的性质不一样。**

上面每一步都是「照着计划做、自己写测试验」。这一节是用户**第一次拿着
浏览器从头点到尾**之后报回来的问题 —— 一共八个，
**全部真实，没有一个是误报，也没有一个被 498 条自动化测试拦住过**。

值得单独记，是因为这八个错分成很清楚的三类，而三类各有各的教训。

### 第一类：我照搬了别人行业的做法（最贵）

**工时模块整个删掉。** 详见 Step 16。

一句话：我做的是英美计时制律所那一套，而中国的提成制律所
**团队成员和律师助理拿的是工资或分成，时间不换算成客户账单**。
硬套下去的结果是所有人应付式补录 ——
**假数据比没数据危险，因为它会被拿去算成本、算人效、算分成。**

★ 这个错在 Step 21 已经露过一次头（用户说"工时不用计"，我照做了但
没回头问"那这个模块还留着干什么"）。**功能失去唯一出口就该当场提出来。**

拆掉之后还留了两条尾巴，都是用户点出来的：

| 尾巴 | 表现 |
|---|---|
| 角色里的 `time.*` 权限点没跟着改 | 咨询功能对所有现存租户**静默不可用**（见下） |
| 收费模式还留着「计时收费」而且是**默认值** | 表单一打开就是一个填不了钱、也出不了账的模式 |

### 第二类：看得到但点不动（四个，同一个病）

| 位置 | 表现 | 根因 |
|---|---|---|
| 看板 14 个指标 | 点哪个都跳到同一张全量表 | drill 不带筛选 |
| 办案流程的依据 | 写着法条编号，点不动 | 纯 `<div>`，而 `lookup` 只在 Port 层**从没透到 HTTP** |
| 文书节标题的「引用 S1、S2」 | 点不动 | 纯文本（正文里的能点，别处的不能） |
| 引用体检表的【S2】 | 点不动 | 纯 `<td>` |

★ 我在 Step 21 自己写下过「**点不开的数字是装饰**」，然后
**在四个地方各违反了一次**。写下原则和执行原则是两件事。

**一条打不开的依据，和没有依据的区别只在于它让人以为查过了。**
律师复核依据的唯一办法是读原文 —— 读不到就只能相信机器。

顺手补的：`/retrieval/lookup`（按标识反查原文，只读、0 成本）。
它早就存在于 `RetrievalPort`，引用体检在用，**但界面拿不到**。

### 第三类：改了代码没改数据（两个）

**① 权限点改名 —— 最隐蔽的一个。**

`time.*` → `consult.*` 改的是代码，**但权限点是存在库里的**。
已建租户的角色上挂的还是 `time.log` 这些死代码，新的谁都没有。

结果不是报错，是**功能静默消失**：菜单不显示、接口 403，
没有任何东西提示你少了点什么。要不是逐条探接口，
得等哪天想记条咨询才发现。

`ensure_default_roles` 帮不上忙 —— 它对已存在的角色**整个跳过**，
刻意不补新权限（新模块上线该给谁由律所决定，不是代码决定）。
**那个设计是对的，但改名不是新增。**

修法是一条迁移（`e2b45c7a1f38`）。其中一个决定：
`time.approve` 和 `time.log_others` **直接删掉不映射** ——
咨询没有审批也没有代录，硬找个新代码塞进去等于凭空发权限。

★ 这已经是第二次踩「新库对、老库错」（第一次是 Step 14/15 的
`ensure_default_rules` 不回填新字段）。**两次都不报错。**

**② 拆模块留下的迁移头。**

删掉 `modules/time/` 之后，`kernel.alembic_version` 里还留着它的分支头，
alembic 去找一个不存在的 revision 然后报 `Can't locate revision`。
**而且是升级时才炸，不是启动时。** 写进 MODULE_GUIDE 第 9 条了。

### 另外两个

**登录后 404。** `login/page.tsx` 跳的是 `/org` —— Step 3 的首页，
早就没了。**18 步没人碰过登录页**，所以一直没暴露。

**建了客户不显示。** 页面上只有「新建主体」，`createClient`
**从头到尾没被调用过** —— 客户表永远只有种子数据。

修完之后用户又报：之前建的两个主体还是不显示。
**我的修复只覆盖了"新建"那条路** —— 已经躺在库里的主体
没有任何办法转成客户，而界面上一个字都没解释为什么。
补了一栏「主体库里还不是客户的」，每行一个「建成客户」。

★ 那一栏顺带证明了一件事：15 个待补里有 8 个是 `DEMO-REV对方X`
这种**对方当事人** —— 他们本来就不该是客户。
**主体和客户不能合并**：主体库要存所有当事人（利冲查的是这个，
漏一个就查不出冲突），客户只是其中签了委托的那部分。

### 顺带做的两件事

**执业资格**（用户提的「律所的律师要看是否有职业资格」）。

`User` 上加了 `license_no` / `license_status` / `licensed_on` /
`license_valid_to` / `license_firm`（迁移 `a7c31e9d4b02`）。三个决定：

| 决定 | 为什么 |
|---|---|
| **分五档不是布尔** | 实习律师不能独立承办、不能单独出庭。做成"有证/没证"就丢了这件事 |
| **过期只警告不拦人** | 年检晚办几天很常见，把案子卡死没道理。但也不能不说 —— "执业中"绿标底下压着三年前过期的证，**比什么都不显示更糟，它让人以为查过了** |
| **注销的人不停账号** | 他办过的案子要留痕，账号一停历史全变"未知用户" |

停止执业 / 已注销的人**挂不了新案件主办**。
职级是所里给的，执业证是司法行政机关给的 —— **两件事，都要查**。

**谁能建客户**（用户提的「除了律师助理，合伙人、独立律师都可以」）。

根因是**独立律师和律师助理是同一个角色**，权限完全一样。
改成两条线各管各的：

```
角色管按钮   crm.manage_party 给「律师」角色
职级管资格   律师助理没有「可独立承办」，拦在 service
```

和主办律师那道检查是同一个开关。要放开就改一行数据。

★ 为什么不把建客户收到管委会手里：律师本来就在自己拉客户，
收上去的结果只会是**律师微信里报一句、助理代录一遍** ——
中间那一遍就是利冲漏检的入口。
